Project: birdOS

birdOS is a purpose-built operating system for exactly one device: the Anbernic RG34XX-SP. It is not intended to be portable or a general Linux distribution.

Active launcher path:
- launcher/bird-launcher.c
- launcher/catalog.generated.h, generated by generate-launcher-catalog.py
- firmware/generate-launcher-bootlogo.py
- kernel/rocknix/build-stock-root-compat.sh
- kernel/rocknix/build-stock-root-early-initramfs.sh
- kernel/rocknix/tests/launcher-runtime-host.c
- related active stock-root tests

Active development workflow:
- Use `./dev-build-and-deploy.sh --changed` for supported birdOS-owned local
  implementation changes.
- Use `./dev-build-and-deploy.sh --all-local` as the complete local rebuild and
  host-test gate at the end of a development cycle.
- Read `DEV_WORKFLOW.md` before changing the workflow or crossing a
  full-release-only boundary.
- `dev-current` is mutable test state. It is never an accepted production
  release, previous production selector, rollback release or archive target.
- Never run the canonical production deployment while `dev-current` or
  `/flash/bird-dev` exists. Run `./dev-build-and-deploy.sh --clean` first.
- If malformed development metadata blocks rollback while `dev-current` is
  selected, use `./dev-build-and-deploy.sh --recover-production`; do not
  reconstruct or guess a production selector.
- A successful `dev-current` test is not production acceptance. Promotion still
  requires the canonical immutable build and its separate physical gate.

Historical muOS launchers, S03birdlauncher, old clean-root experiments, committed launcher objects, and old installers are not the active implementation unless an active build script explicitly references them.

Optimization priorities, in strict order:
1. Boot speed into a genuinely usable menu. Do not visibly present interactive menu controls until launcher input is working.
2. Button-to-photon interaction speed and usability.
3. Battery efficiency and elimination of unnecessary wakeups.
4. Memory efficiency.

Fixed RG34XX-SP paths, display geometry, input names, dimensions, framebuffer behavior, policies, and device assumptions are intentional. Do not report them as portability problems or replace them with generic hardware discovery without a measured reason.

Launcher architectural constraints:
- Keep the launcher freestanding AArch64 Linux.
- No libc dependency.
- No dynamic loader.
- No SDL.
- No DRM compositor dependency.
- No font library.
- No runtime image decoder.
- No runtime configuration parser.
- No dynamic allocation unless explicitly justified and approved.
- No rendering thread.
- No fixed-rate frame loop.
- No general widget framework.
- No runtime plugin system.
- Keep direct framebuffer and direct evdev ownership.
- Keep ordinary idle blocking in ppoll with no periodic frame wakeup.
- Keep storage, application setup, audio, networking, controls, and optional services outside the launcher.
- Keep the embedded catalog; never add a boot-time ROM scan.

Readiness contracts:
- First-frame ready means the visible menu is interactive and input works.
- First-frame ready must not wait for ROM storage or the complete application runtime.
- Storage remains asynchronous.
- A selection made before storage readiness may be represented by exactly one cancellable pending intent.
- Application readiness is a separate later contract.
- Do not conflate visible frame, usable frame, storage readiness, and application readiness.

Accepted behavior that must remain:
- Main menu sections Play, Listen, Read, and Watch.
- D-pad navigation and wrapping.
- Paging.
- A selection.
- B navigation and main-page reload.
- Favorites persistence.
- Cached catalog browsing before storage is ready.
- Pending launch behavior before storage readiness.
- Exact previous-page and previous-selection return after content.
- Game and media request handoff.
- Charging and battery percentage display.
- Input reconnect recovery.
- No ordinary full-screen redraw caused merely by storage becoming ready.
- No duplicate content launches.
- No launcher/input ownership loss during later initialization.

Performance rules:
- Optimize measured memory traffic and syscall count before microscopic arithmetic or branch tricks.
- A normal selection movement should not redraw the entire framebuffer.
- A battery update should not redraw the entire framebuffer.
- Input processing should take priority over background storage and power events.
- Do not place filesystem persistence or verbose logging before the visible response to navigation.
- Do not claim a hardware timing improvement without hardware measurements.
- Host-side metrics may be described as instruction, syscall, byte-write, or synthetic-render improvements, not as measured device latency.

Implementation rules:
- Preserve a full-render fallback for initial render, view changes, recovery, and uncertain framebuffer state.
- Generate data at build time where practical instead of computing or parsing it at runtime.
- Generated catalog files must be changed through their generator, not hand-edited.
- Prefer explicit fixed structs and enums over abstractions.
- Keep hot rendering functions static and visible to the optimizer in the same translation unit or through included static-inline/generated headers.
- Do not add product features while doing performance work.
- Do not change the visual design unless the task explicitly asks for visual changes.
- Do not commit, push, or open a pull request unless explicitly instructed.

For every implementation task:
1. Inspect the active call path before editing.
2. State the concrete hot path being changed.
3. Preserve accepted behavior.
4. Add or update focused tests.
5. Run relevant launcher and catalog tests.
6. Compile both the final-root and early-initramfs launcher variants where the environment permits.
7. Report changed files, tests run, measured host-side differences, and anything requiring RG34XX-SP verification.
8. Be honest when hardware behavior cannot be proven in the current environment.

Implementation summaries must put a short explanation of why the previous
implementation existed before describing what changed. Independently testable
changes may be batched into one hardware cycle when each active path, assertion,
host test, measured delta, and rollback boundary remains explicit.
